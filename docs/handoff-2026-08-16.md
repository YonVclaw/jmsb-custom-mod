## THE OPEN INVESTIGATION: "it's raining drones"

This is the one live unknown. Read this before touching `jmfsb_uas`.

**Symptom:** drones fall out of the sky continuously on the dedicated
server; the user reports they arrive with no AI aboard.

**What the evidence actually shows** (server RPT
`arma3server_08_15_2026_220508.rpt`, build 716):

- 47 patrol drones spawned, crewed, and flew. **Zero** `spawns with no
  crew` warnings, **zero** killed, **zero** deleted.
- Yet `patrol(s) up` reads **0 for every side on every 60-second tick** —
  in that log, in every earlier server log, and in **every hosted-SP log on
  record**. The ledger empties with nothing logging a death.
- So: drones are not dying of anything that reports. Either the ledger
  loses them (the prune is its only remover) or they leave the world in a
  way nothing observed.

**Ruled out with source reads, do not re-litigate:**

- Drongos Drone Tweaks jammers — its `DDT_fnc_JamDrone` does delete crew,
  but only runs off its jammer backpack (`DDT_DroneJammerPack`) or placed
  heavy jammer objects. The user has neither. DDT's drone *register* is
  benign (mutes voices, disables combat reflexes).
- ELKA AntiUAV — a pure weapon mod, no scripts at all.
- Crew-class failure — the spawn path retries `createVehicleCrew`,
  hand-seats the drone's own declared crew class, then the side's vanilla
  `*_UAV_AI`, and **deletes the airframe with a named warning** if all
  three fail. No such warning has ever appeared.

**Instrumentation waiting for a server run on ≥717:**

- `patrol drone up: <class> for <side> at <grid>` — every spawn.
- `patrol drone killed at <grid> by '<class>' (<name>)` — names the killer.
- `patrol drone DELETED (not killed)` — a script or GC removed it.
- `prune drops <x> - isNull <b>, alive <b>` — why the ledger dropped an
  entry (fnc_livePatrols).
- `'<class>' cannot self-fly - it stalled onto the deck` — the 45-second
  stall test, which also deletes the husk.

**Next action:** get a server RPT from build ≥717, grep `patrol drone`,
`prune drops`, `stalled`. One of those five lines will name the mechanism.
Do not theorise further without it — four theories have already died.

**Also found while investigating:** the drone module's per-side class
fields were stocked with FPV/loitering **munitions** (`B_SwitchBlade_600`,
`I_Crocus_AP/AT`, `I_KVN_AP`). Those have no autonomous pilot and tumble
whatever crew they carry. Patrol fields want AI-flyable recon airframes;
munitions belong to the ambience kamikaze module's field. The stall test
now names any that slip in.

Mitigation already shipped (715): losses regenerate **one per side per
minute** (`UAS_REGEN_PER_TICK`, keyed on a seeded flag, not the live
count). Even at worst the sky cannot rain.

## The five bug families (full-mod audit, build 711)

Three audit agents plus a manual pass fixed ~25 verified bugs. Grep for
these first in any future work — every one appeared more than once:

1. **Stale callers after a signature refactor.** `fireBarrage` was
   refactored to `[pos, rounds, spread, shell, window]` and **three**
   callers still passed the old ammo-first shape (reaction, qrf, leaders),
   silently rescued by defaults. When you change a shared function's
   signature, grep every caller in the same turn.
2. **`exitWith` inside a `then{}`** exits only that block. Cost: reaction's
   SATCOM exemption never exempted anyone; hacking tower failures printed
   "Intrusion FAILED" and then delivered the hack anyway.
3. **Server-set values read on clients**, invisible in hosted SP because
   host == server. Cost: the whole radio-detection leg dead in MP, the
   hacking product menu empty for every remote player, pad rearm/refuel
   silently failing. Fixes: `publicVariable`, published client-safe
   summaries (`adapter_alive` `commandersPub`/`taorPub`), or per-unit
   variable mirrors (`reaction` `flaggedUntil`).
4. **Never-written GVARs killing whole addons.** `jmfsb_jamming` was
   entirely dead — nine model knobs read everywhere, defined nowhere.
   `equipment` and `boarding` were dead behind an `EGVAR(main,jmfsb_enabled)`
   gate nothing ever set.
5. **Locality.** Argument-local commands on remote objects
   (`setVehicleAmmo`, `setFuel`, `fullHealLocal`, ACM resets) need
   `remoteExec` at the owner.

Plus a recurring HEMTT trap: **`INFO_x`/`WARNING_x` macro arguments cannot
contain commas** — `[a,b]`, an inline `getVariable [x, y]`, or a `select`
over an array literal all read as extra macro arguments. Hoist to a local
first. Bare `break` is not an SQF command either.

### 1-3. "Size to fit the red / blue / green box"

Three boxes drawn round three panels, all saying the same thing: **the
content does not fill its frame.**

- **Red — the live-tile band** (`tacpad_apps/fnc_panelTiles`,
  `DEFAULT_TILES [0.008, 0.031, 0.60, 0.11]`). Six tiles are drawn, the row
  ends short of the frame's right edge, and a `+1` sits in the gap - a
  seventh tile that had no room. Tiles should size to the band so all of
  them fit edge to edge. `TILE_W` in `tacpad/shared.inc.hpp` is a fixed
  fraction; the fix is to derive tile width from the frame width and the
  tile count rather than shipping a constant.
- **Blue — the squad rail** (`tacpad_apps/fnc_panelSquad`,
  `DEFAULT_SQUAD [0.008, 0.20, 0.150, 0.60]`). Two men listed at the top,
  the legend and REFRESH pinned to the foot, and a tall dead gap between
  them. The rail deliberately keeps its placed height (the comment at the
  `_bodyH` block explains why: sized to the section it was two inches tall
  for a fire team). So the frame stays and the CONTENT has to fill it.
- **Green — the reader** (`tacpad_apps/fnc_panelReader`,
  `DEFAULT_READER [0.72, 0.031, 0.27, 0.66]`). Three threads listed, then a
  large empty area above OPEN FULL / NEW. Same shape of problem: the list
  should use the height it has.

Note the tension with `EFUNC(tacpad,fit)`, which does the OPPOSITE - it
shrinks a panel to the rows it drew, and exists because an empty reader
used to be "a wall of white over the map". Neither the squad rail nor the
reader calls `fit` today (only tiles and tools do). **Decide which way each
panel goes and say so in the code**: either the frame shrinks to the
content (`fit`) or the content spreads to the frame. The user's boxes are
drawn around the FULL frames, and their note says "size to fit the box",
which reads as: keep the frame, fill it. Recommend confirming with one
screenshot before doing all three.
